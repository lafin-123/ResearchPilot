# Research Pipeline

The default order is experiment before paper. Do not jump to a manuscript because writing is easier than running the study.

## Native automation contract

Use only bundled project capabilities, never pwsh/bash, raw HTTP, research CLI or generic file write/edit for the automatic workflow. Required servers: rp_evidence, rp_artifacts, rp_writing; Python must be explicitly configured. `workspace_inventory` discovers IDs; `literature_search`/`reference_add_doi` retrieve real metadata after approval; `artifact_read` reads plans/code/run outputs; `project_artifact_write` writes all stage notes and handoff JSON; `experiment_create` registers agent-authored study/analysis/audit source; `experiment_run` executes it with separate approval and 30–120s bound; `figure_create_spec` creates JSON/SVG/native PPTX directly from your actual-data inline spec; `manuscript_write` writes the registered manuscript. Missing capability or denied approval is a blocker, not a reason to bypass the boundary.

Analysis and audit JSON must be actual outputs from executed agent-authored analysis/audit experiments, read and copied exactly from run artifacts, with input paths/hashes and limitations. Status passed means only declared mechanical checks passed. Citation/DOI matching does not establish full-text support; keep humanReviewRequired=true and explicit unresolved scientific/source-support review, never forge supportReviewed flags. Simulation must be labeled as simulation and have actual computed observations. All code, figures and manuscript prose must be generated by the research agent, not seeded by a harness.

## Stages

1. Literature: scope, screen, synthesize, save references/research-brief.md.
2. Hypothesis: falsifiable claims, baselines, metrics, success criteria, risks.
3. Experiment design: protocol, smoke test code, experiment plan.
4. Experiment execution: create/run experiments, capture run IDs, logs, metrics, artifacts.
5. Analysis: compare baselines, quantify uncertainty, ablations, failures.
6. Figures/tables: publication-quality figures from run artifacts.
7. Manuscript: DOCX and/or LaTeX from the claims-evidence map.
8. Review: audit claims, citations, numbers, reproducibility, limitations; revise.

## Workflow

### 1. Start with the evidence inventory

Check what already exists. Do not rerun a stage whose artifacts are present unless the user asks. Use scripts/check_pipeline.py.

### 2. Stage transitions

At each boundary:

- follow the current application prompt's enforced artifact gate (it overrides legacy example paths);
- write `exports/pipeline/<runId>/<stage>.json` with the exact runId, stepId and stage, version 1, status `ready`, arrays artifacts/referenceIds/experimentIds/runIds/figureIds/documentIds and blockers;
- list project-relative nonempty files actually inspected, including registered experiment code and real files inside each cited successful run's artifact directory;
- analysis also requires `exports/data-audit.json` and `exports/statistical-analysis.json`; review requires citation audit and reproducibility JSON, all with version=1, status=passed, blockers=[];
- figures require a non-demo native spec JSON, SVG and editable PPTX; sourceLabel identifies the cited run ID and actual source artifact. Raster images are not native editable output;
- never set ready with unresolved blockers; a fluent completion message does not pass the gate;
- the app saves a verification receipt with SHA-256 hashes. This checks structural evidence, not scientific correctness;
- failed stages retry in place and never silently advance.

Then:

- verify the required artifacts exist;
- write a handoff using templates/stage-handoff.md;
- update exports/pipeline-summary.md;
- state the next stage and any unresolved risks.

### 3. Checkpoints

Pause for approval before:

- expensive/local or remote runs;
- changing the primary metric or success criterion;
- deleting artifacts;
- making a claim that cannot be traced to a run/citation;
- sending data to an external service.

### 4. Automation behavior

When asked to run everything:

1. Summarize the plan and checkpoints.
2. Complete literature and hypothesis first and save artifacts.
3. Run a smoke experiment, then scale.
4. Continue only when the current stage produced verifiable artifacts.
5. Stop at approvals, failures, or contradictory evidence.
6. Finish with a review pass and a list of unverified claims.

### 5. Failure handling

If a stage fails, report the exact failure and remain at that stage. Never skip a failed experiment to write results. See references/failure-recovery.md.

### 6. Final audit

~~~powershell
uv run --no-project --python 3.12 python .agents/skills/research-pipeline/scripts/check_pipeline.py
uv run --no-project --python 3.12 python .agents/skills/research-pipeline/scripts/summarize_pipeline.py
~~~

## Quality gates

- [ ] Every run referenced exists and completed.
- [ ] Every number traces to a run artifact.
- [ ] Every citation is real and in the library.
- [ ] Negative and failed results are reported.
- [ ] The manuscript states limitations.
- [ ] The summary lists verified, uncertain, and unverified work.

## Failure modes

- Writing the paper before running the experiment.
- Advancing a stage because a file exists but is empty.
- Treating a generic model response as an experiment result.
- Losing artifacts between stages.
- Silence about a failed run.
